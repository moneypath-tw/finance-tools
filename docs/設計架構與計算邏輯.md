# 錢路設計架構與計算邏輯

給要改程式的人（含 AI）看：每個概念由哪支檔案的哪個函式擁有、資料怎麼流、數字怎麼算、改的時候要守哪些防線。使用者操作說明見 [README.md](../README.md)；逐輪變更見 [進度紀錄.md](../progress/進度紀錄.md)。本文只寫結構與規則，函式內的細節以程式碼註解為準。

## 一、定位與硬限制

| 項目 | 規則 | 由誰守住 |
|---|---|---|
| 執行環境 | 純前端靜態網頁，無後端、無登入、無第三方執行期套件；`file://` 下載版與 GitHub Pages 線上版是同一份程式 | `package.json` 只有 Node 內建測試器 |
| 網路 | 頁面不對外連線（CSP `connect-src 'none'`），外部數字是離線快照 | `tests/core.test.mjs`「CSP 封住資料外流管道」 |
| AI | 不用 AI；所有結果由純函式算出，可重跑、可測 | — |
| 資料 | 只存在使用者瀏覽器（或使用者自己綁定的 JSON 檔）；公開倉庫只放範例假資料 | `scripts/check-no-real-data.sh`（pre-commit 與 CI） |
| 使用對象 | 20–50 歲一般使用者：少思考也算得準、自己的狀況一眼看懂、細節按需展開 | 結論／編輯兩種檢視模式 |

## 二、檔案分工與載入順序

`index.html` 依下表順序以一般 `<script>` 載入（不是 ES module），每支檔案在全域定義一個物件；後面的檔案可以用前面的。例外：`Planning` 在呼叫時才取用 `Money`（`payCycle` 內註明），所以兩者的載入順序不能改成在定義時就互相引用。

| 順序 | 檔案 | 全域名稱 | 擁有的東西 | 會不會碰畫面 |
|---|---|---|---|---|
| 1 | `shared/frame-guard.js` | — | 防 iframe 嵌入；必須是 `<head>` 第一支 | 只隱藏頁面 |
| 2 | `shared/reference-data.js` | `REFERENCE_DATA` | 外部制度與官方預測數字（通膨、勞健保、學貸、房貸、基本工資、勞基法工時），每筆附官方網址與取得日期 | 否 |
| 3 | `shared/config.js` | `PLANNING_RULES`、`DEFAULT_CONFIG`、`DEFAULT_LEDGER`、`ALLOCATION_PURPOSES`、`DEFAULT_SCENARIOS`、`WAGE_REVERSE_SCENARIO` | 本工具自訂的規劃規則、預設值、分配用途清單、成本試算範本 | 否 |
| 4 | `shared/snapshots.js` | `Snapshots` | 帳戶核對模式（只記餘額）的推算 | 否，純函式 |
| 5 | `shared/validation.js` | `Validation` | 所有輸入、匯入、載入的驗證與修復（`repairWorkspace`） | 否，純函式 |
| 6 | `shared/planning.js` | `Planning` | 分配、狀態、轉帳指示、首頁結論、緊急預備金、健檢、習慣、收入目標等規劃演算法 | 否，純函式 |
| 7 | `shared/money.js` | `Money` | 金額單位換算與格式、匯率、薪資與勞健保、固定項目每月推估、租屋、貸款、成本試算、趨勢圖 SVG | 否，純函式 |
| 8 | `shared/io.js` | `IO` | 保存（localStorage、IndexedDB 滾動版本、綁定檔案）、匯入匯出、多分頁衝突、離開前保存 | 只回報狀態 |
| 9 | `shared/app.js` | `App` | 狀態持有者：把設定與帳本組成各純函式的輸入，再渲染畫面 | 是 |
| 10 | `shared/sw-register.js`＋`sw.js` | — | 線上版離線快取，只快取程式檔；網路優先且繞過 HTTP 快取 | 否 |

分層原則：**計算放在 4–7 的純函式**（Node 可直接測），`app.js` 只負責「從狀態取值 → 呼叫純函式 → 渲染」。新的計算規則寫進 `Planning` 或 `Money` 並加單元測試，不寫在渲染函式裡。

## 三、資料模型

工作區（`App` 的 `workspaceSnapshot()`）由四部分組成，整包保存、匯出、匯入：

| 部分 | 內容 | 預設來源 |
|---|---|---|
| `config` | 介面狀態、通膨率覆寫、分類、帳戶（`accountProfiles`）、固定出入帳（`recurringCashFlows`）、首頁設定（`dashboard`：各用途搭配帳戶、勾選的成本目標）、勞健保費率、出生年、快速健檢輸入（`quickPlan`） | `DEFAULT_CONFIG` |
| `ledger` | 帳目 `entries`（收入、支出、轉帳、願望清單）與帳戶核對紀錄 `snapshots` | `DEFAULT_LEDGER` |
| `scenarios` | 成本試算情境（買房、自建、旅費、學貸、喪葬、養老、FIRE 與使用者新增的） | `DEFAULT_SCENARIOS` |
| `wageReverseScenario` | 工時反推設定 | `WAGE_REVERSE_SCENARIO` |

| 規則 | 說明 |
|---|---|
| 金額單位 | 一律整數「分」（`*Cents`）。推算出的台幣金額用 `Money.roundYuan` 四捨五入到整數元；顯示整數元。外幣金額與使用者輸入的利率保留小數 |
| 外幣 | 不設共用匯率表；每筆帳目或情境自帶 `currency`＋`rateToTWD`，由 `Money.entryTWDCents` 換算 |
| 帳目狀態 | `projected`＝固定項目產生的預測；`realized`＝已入帳。只有已入帳的帳目影響餘額與實際花費；預測帳目可在帳本改金額後「確認入帳」 |
| 預測帳目 ID | `recurring-<flowId>-<YYYY-MM>`（租屋補助另加 `-subsidy`），同一個月同一個項目只會有一筆 |
| 日期 | 一律用本機時區的 `YYYY-MM-DD`（`Money.ymd`）；不用 UTC 的 `toISOString` 取當天日期 |

## 四、生命週期：載入、遷移、修復、保存

```
localStorage（或匯入／綁定檔案）
  → App.restoreWorkspace
      → migrateConfig        舊欄位一次轉成新欄位（唯一轉換路徑：還原與單獨匯入設定都走這裡）
      → Validation.validateLedger   帳本不合法才拒絕
      → Validation.repairWorkspace  可修的就地修好（帳戶被刪、同帳戶轉帳、缺月工時…）
      → Validation.validateWorkspace（情境內容錯誤不擋載入，改在試算畫面提示）
  → materializeDueRecurringEntries  依固定項目補產生預測帳目；本月每次重算，已入帳的不動
  → renderAll
  → 使用者修改 → IO.markDirty → saveCurrent（localStorage）＋ IndexedDB 滾動版本 ＋ 綁定檔案
```

| 規則 | 原因 |
|---|---|
| 載入不是全有全無：先修復再驗證；真的載不進時把原始資料備份到 `finance-tools.workspace.rejected` 並提供下載 | 2026-10-20 曾因單一欄位不合法整份不載入，自動保存再把預設值蓋回去 |
| 舊存檔的轉換只寫在 `migrateConfig`／`restoreWorkspace`，內部程式直接使用正規化後的資料 | 入口正規化一次，不在各處重複防呆 |
| 使用者從沒改過的範例值（例如舊版範例目標）在遷移時改成「不設定」，並留下標記，之後使用者自己選的不再改 | 範例值不能被當成使用者自己的資料 |
| 另一個分頁寫入較新的工作區時，這個分頁停止保存並提示 | 防止舊分頁覆蓋新資料 |
| 月中停用或刪除固定項目：只清本月仍是預測的帳目，已入帳的與過去月份一律保留 | 刪使用者資料要使用者決定 |

## 五、每月計畫：一條管線算出首頁所有數字

首頁的每個數字都來自 `App.currentMonthSavingsHealth()` 的同一次計算；不同區塊不各自重算。

```
recurringSummary()         固定出入帳每月推估（Money.calcRecurringMonthly；學貸、房貸先同步成固定支出）
  → monthlyPlan()          收入、固定支出、生活費、每月可存＝收入－固定支出－生活費
  → cycleFacts()           本期帳務事實：發薪週期、餘額、本期應扣與已扣、實際生活花費、各帳戶轉入
  → emergencyPlan()        緊急預備金（Planning.emergencyFund）
  → poolGoalSavings()      成本目標的已存金額（同帳戶的錢只算一次）
  → allocateMonthly()      依序分配收入 → 分配表 rows
  → transferPlan()         依目的帳戶合併的轉帳指示
  → allocationStatus()     每列狀態、原因與一句可照做的指示
  → homeVerdict()          首頁一句結論＋解方＋分配長條
```

### 5.1 概念與唯一擁有者

| 概念 | 唯一定義處 | 誰讀它 |
|---|---|---|
| 本期 | `Planning.payCycle`：主要收入（金額最大的固定收入）發薪日到下次發薪前一天；發薪日超過月底天數用月底 | 分配狀態、生活費進度、建議值、習慣 |
| 每月收支 | `App.monthlyPlan` | 首頁、成本試算存款版達成時間、FIRE 連動 |
| 本期帳務事實 | `App.cycleFacts`（只看已入帳帳目與實際餘額） | 分配狀態、轉帳指示、緊急預備金與目標可用餘額 |
| 生活花費 | `Planning.isLivingSpend`：已入帳的支出、不是固定項目產生、記在計入生活花費的帳戶 | 本期進度、建議值、習慣分類 |
| 計入生活花費的帳戶 | `Planning.livingSpendAccounts`：使用者勾選優先；否則自動（生活費／固定支出／薪資帳戶、信用卡、其他可動用帳戶；排除只放存款的帳戶與投資） | 同上 |
| 本期還要付的支出 | `Planning.spendingNeedByAccount` | 緊急預備金可用餘額、目標保留額、轉帳缺額（同一份） |
| 緊急預備金 | `Planning.emergencyFund` | 首頁、健檢、FIRE |
| 分配用途清單與名稱 | `ALLOCATION_PURPOSES`（`config.js`）；`Planning.purposeLabel` 找不到就丟錯 | 分配表、帳戶選單、修復 |
| 規劃門檻 | `PLANNING_RULES`（`config.js`） | 全部 |
| 外部數字 | `REFERENCE_DATA`（`reference-data.js`） | 全部；使用者覆寫值存在 `config` |

### 5.2 分配順序（`Planning.allocateMonthly`）

收入依下列順序分配，前面的分完才輪到後面；不夠的部分記成該列的 `shortfallCents`：

| 順序 | 用途 | 金額 | 必要 |
|---|---|---|---|
| 1 | 固定支出 | 固定項目每月推估（已約定的款項先付） | 是 |
| 2 | 生活費 | 使用者設定的生活費預算 | 是 |
| 3 | 緊急預備金 | 缺口 ÷ `PLANNING_RULES.emergencyFillMonths`；固定儲蓄轉入同帳戶時取兩者較大 | 是 |
| 4 | 一般儲蓄 | 讓應儲蓄合計至少達 `savingsRateTarget`；固定儲蓄轉到別的帳戶時至少是那筆 | 是 |
| 5 | 成本目標 | 依期限先後；每月需存＝（目標－已存）÷ 剩餘月數；期限已過或情境不合法的不納入 | 否 |

加總恆等式：所有列的 `allocatedCents`＋`unallocatedCents`＝收入。首頁長條就是這幾段，瀏覽器實測檢查加總＝收入。

### 5.3 關鍵公式

| 數字 | 公式 | 擁有者 |
|---|---|---|
| 通膨後金額 | `今日金額 × (1＋年通膨率)^(月數 ÷ 12)`，一律複利 | `Planning.futureValue` |
| 實質報酬率 | `(1＋名目) ÷ (1＋通膨) − 1` | `Planning.realRate` |
| 緊急預備金目標 | 每月（未扣補助的必要固定支出＋生活費）× 目標月數（限制在 `emergencyMonths` 的 min～max） | `Planning.emergencyFund` |
| 緊急預備金可用餘額 | 指定帳戶餘額－該帳戶本期還要付的支出 | `App.emergencyAvailableCents` |
| 本期建議提撥 | 用**本期開始時**的餘額算（扣回本期已入帳的轉入），轉入後建議額不會跟著變小 | `App.balanceAtCycleStart` |
| 每日可花 | （生活費分配額＋未分配的錢－已花）÷ 本期剩餘天數，無條件捨去到整數元（不高估） | `Planning.allocationStatus` |
| 生活費建議值 | 近 `livingSuggestCycles` 個完整發薪週期實際生活花費的中位數，無條件進位到百元；只算開始記帳後的週期；按下按鈕才寫入預算 | `Planning.livingSpendHistory` |
| 需要的收入 | 最低＝付得起支出；建議＝最小的 I 使 I＝支出＋max(儲蓄下限, 儲蓄率基準 × I) | `Planning.requiredIncome` |
| 工時／時薪目標 | 只調整一份收入；淨額換稅前用該收入目前的淨／稅前比例；結果無條件進位；不低於基本工資 | `Planning.workTarget` |
| 帳戶核對推算用掉 | 期初餘額＋期間計畫存入－期末餘額；負數顯示「多出」；比較各期用每 30 天換算 | `Snapshots.periods` |

### 5.4 狀態判斷（`Planning.allocationStatus`）

狀態分 `ok`（綠）、`watch`（留意）、`short`（不足）、`none`（不判斷）。每個非 ok 狀態附一個簡短原因 `tag` 與一句可照做的 `action`（動詞＋金額＋目的地）。

| 情況 | 判斷 |
|---|---|
| 沒有任何已入帳帳目且帳戶餘額全為 0 | `none`「尚未記帳」，不判紅（新使用者一打開不會全紅） |
| 收入不夠分配到這一列 | 原因一律寫「收入不夠分配」，和「尚未轉帳」分開講 |
| 固定支出：扣款日已過仍是預測 | `watch`「待確認入帳」 |
| 生活費：已花超過可花用 | `short`「超支」；超過預算但沒超過可花用 → `watch` |
| 儲蓄類：固定儲蓄的預測轉帳足額 | `watch`「待確認入帳」，不判不足 |
| 儲蓄類：發薪後 3 天內還沒轉 | `watch`「待轉入」；之後 → `short`「尚未轉入」 |
| 儲蓄類搭配的是薪資入帳帳戶 | `watch`「無法追蹤」，建議改搭配獨立帳戶 |

### 5.5 轉帳指示（`Planning.transferPlan`）

- 依**目的帳戶**合併成一句（例如「從薪轉轉 X 元到儲蓄（緊急預備金、一般儲蓄）」），不逐列重複。
- 支出用途補到夠付本期剩下的支出；儲蓄用途每期存入分配額－已轉入－固定儲蓄預計轉入。
- 同帳戶多用途時，本期轉入的錢依分配順序先算支出、剩下才算存入；存入的錢不算可用餘額。
- 薪資入帳帳戶本身不用轉，只回報支出缺額。
- 分配狀態的「已轉入」讀 `transferPlan.rowFacts`，所以狀態與指示一定是同一個數字。

### 5.6 首頁呈現

| 模式 | 內容 |
|---|---|
| 結論模式（預設） | 一句結論（`homeVerdict.headline`）、每天可花、分配長條、生活費滑桿（放開即重算並保存）、緊急預備金進度條、最多 3 件要做的事；計算過程收在「怎麼算的」 |
| 編輯模式 | 再加健檢結論卡、摘要卡、範例值提示列、完整設定 |

解方規則（`homeVerdict`）：差額不超過生活費時說「生活費降到多少就存滿」；否則說「增加收入或減少固定支出」。

## 六、成本試算與健檢

| 功能 | 擁有者 | 要點 |
|---|---|---|
| 情境類型與試算 | `Money.getScenarioType`／`calcScenario`／`toScenarioSummary` | 不合法的情境（例如退休年齡小於目前年齡）標示無法計算，不把錯誤金額帶進首頁 |
| 房貸、學貸 | `Money.calcMortgageRepayment`／`calcStudentLoanRepayment` | 勾選「納入固定支出」時由 `App` 同步成系統管理的固定項目 |
| 旅費 | `Money.tripQuantity`／`calcOneTimeScenario`；選項在 `TRIP_BASES`、`TRIP_DESTINATIONS` | 情境有 `trip`（目的地、天數、人數）才啟用；小計＝單價 × 數量（晚數＝天數−1）× 匯率（目的地貨幣項目用情境的 `rateToTWD`，不內建匯率）；目的地沒有官方通膨預測就不套用通膨；舊存檔在 `Validation.normalizeScenario` 遷移，總額不變 |
| 快速健檢 | `Planning.assess` | 有利／基準／壓力三情境；壓力＝收入 −20%、通膨 +1.5 個百分點、零報酬；緊急預備金不可同時充當目標本金 |
| FIRE | `App` 的 FIRE 渲染＋`Planning` | 退休前總需求＝退休資產目標＋其他目標＋緊急預備金；開啟連動時全部由帳本與首頁帶入 |
| 習慣與達成預測 | `Planning.cycleReports`／`habitInsights`／`goalForecast` | 存下＝收入－全部支出（互轉抵銷）；提醒門檻在 `PLANNING_RULES.habitIncrease` |

## 七、安全邊界

| 威脅 | 防護 | 測試 |
|---|---|---|
| 資料外流 | CSP `connect-src 'none'`；無任何 fetch | `tests/core.test.mjs` CSP 測試 |
| 點擊劫持 | `frame-guard.js`（Pages 無法設 frame-ancestors 標頭） | 防嵌入測試 |
| HTML 注入 | DOM 一律 `el()`＋`textContent`；`innerHTML` 只准清空或放已跳脫的趨勢圖 | innerHTML 掃描測試 |
| 行內樣式被 CSP 擋 | 不寫行內 style | 行內樣式測試 |
| 惡意匯入 | 匯入上限 5 MB、驗證後才套用、不覆蓋現有資料 | 攻擊面回歸測試 |
| 部署後拿到舊程式 | `sw.js` 網路優先、`fetch` 帶 `cache: 'no-cache'` 繞過 HTTP 快取；`PRECACHE` 必須與 `index.html` 載入清單一致 | PRECACHE 測試、`npm run browser-check` |
| 真實資料進公開倉庫 | `.gitignore`＋`check-no-real-data.sh`（pre-commit 與 CI） | CI |

|---|---|---|
| `npm test` | `tests/core.test.mjs`：純函式、驗證、遷移、單一來源掃描、攻擊面 | 每次改動 |
| `npm run browser-check` | `scripts/online-browser-check.mjs`：用本機 Chrome 載入舊版存檔與首訪狀態，檢查畫面數字一致、保存、離線快取 | 改到保存、離線快取、頁面載入或首頁數字 |
| `bash scripts/check-no-real-data.sh` | 隱私掃描 | pre-commit 與 CI |

防線原則：
- 修一個「兩處數字不一致」的問題，要加一個比對兩處輸出的測試；收掉一類重複，要加一個掃原始碼的測試（例如「單一權威來源：日期字串、匯率換算…」）。
- 新測試要先在舊程式碼上失敗（`prove_check_fails.py`），才算有擋到。
- 有既存狀態（localStorage、舊存檔）分支的修改，必須用 `browser-check` 帶舊存檔實際跑一次。
- 瀏覽器實測遇到 alert／confirm 會自動關閉並判失敗，正常流程不要觸發原生對話框（目前只有載入失敗時的備份下載詢問）。
