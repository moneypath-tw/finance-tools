# 生活費與帳本頁整併規劃

狀態：規劃（2026-11-16 定案，尚未動工）。動工後把本檔結論併進《設計架構與計算邏輯.md》第 5 章，並刪除本檔。

## 一、使用者實際的記帳方式（設計前提）

- 日常小額不逐筆記，只把**特別花費**記進明細。
- 帳戶核對「想到才做」，間隔不規律。
- 因此**生活費不是明細加總**，而是帳戶餘額的殘差：餘額減少量，扣掉固定支出、明細裡的特別花費、專用帳戶進出、浮動收支，剩下的就是沒記錄的日常生活費。

## 二、現況問題（已查程式）

| 問題 | 位置 | 後果 |
|---|---|---|
| 估算有 3 個來源，依優先序切換：近 3 期明細中位數 → 近 30 天明細換算 → 核對推算 | `app.js` `livingEstimateSource` | 只記特別花費的人，前兩種會得到「特別花費」而不是生活費，數字偏低；來源變了數字會跳 |
| 註解寫「核對推算優先」，程式卻是明細優先 | `app.js` 1146 行 vs `livingEstimateSource` | 註解與行為不一致 |
| 核對推算以「兩次核對之間」為單位，不對齊發薪週期；最新一次核對之後沒有結果 | `Snapshots.periods`／`livingEstimate` | 週期頭尾沒有明確數字；間隔太短就不估 |
| 生活費相關說法並存：生活費預算、生活花費推估、建議值、最低生活費、每日可花 | `app.js` 首頁、`planning.js` | 使用者分不清哪個是哪個 |
| 計入帳戶靠角色自動猜（已有勾選與「改回自動」，但看不到每個帳戶為何計入） | `Planning.livingSpendAccounts`、`app.js` 942 行 | 判斷結果不透明 |
| 帳本頁 6 塊並列：個人設定、核對、浮動收支、新增紀錄、明細、摘要 | `index.html` panel-ledger | 輸入主流程被設定與核對擠到下面 |

## 三、目標模型：一條數字鏈

```
生活費預算（使用者設）→ 實際（系統算，殘差）→ 每日可花（預算 − 本期已花）÷ 剩餘天數
```

只留這三個詞；刪「最低生活費」「建議值」。建議值改成「實際」旁的按鈕「套用為預算」。

## 四、實際生活費怎麼算（`Snapshots` 新函式，唯一擁有者）

輸入：核對紀錄、固定項目、手記帳目、計入帳戶清單、發薪日。

1. 相鄰兩次核對 S1（日期 d1）、S2（d2）：
   殘差 U ＝ （S1 計入帳戶合計 ＋ 期間排程收入與手記收入 ＋ 轉入 − 轉出）− S2 合計 − 排程固定支出 − 手記特別花費；浮動收支與專用帳戶進出先排除。此式沿用 `Snapshots.periods` 的 `livingCents`，不重寫。
2. 每天速率 u ＝ U ÷ (d2 − d1)。
3. 發薪週期（`Planning.payCycle`）頭尾對齊：完整落在 d1～d2 之間的週期，實際 ＝ u × 週期天數，標「實測」。
4. 部分重疊或落在最後一次核對之後的週期：沿用最近一段的 u，標「推估」。週期被兩段核對切開時，各段按天數用各自的 u。
5. 最近兩次核對相隔少於 14 天（`minDays`）且沒有更早的核對可併入：不估，畫面寫「還不能估，再核對一次更準」。
6. 每日可花：本期已花 ＝ 最近 u × 本期已過天數（已記的特別花費另外是特別花費，不重複算）；剩餘天數照發薪週期。
7. 回傳 `{ perCycle: [{start, next, cents, kind: 'measured'|'estimated'}], per30Cents, basis: { from, to, days }, ready }`，所有顯示處只讀這一份。

### 邊界情形（動工時各寫一個測試）

- 只有一次核對：不估。
- 核對跨月、跨發薪日、跨多個週期。
- 核對期間有浮動收入／支出、專用帳戶轉入。
- 某帳戶只在第二次核對出現（`isNew`）。
- U 為負（錢變多了，通常是漏記收入）：不當生活費，提示「這段期間多出 X，可能有未記的收入」，該段不納入。
- 同一筆固定支出手記又排程（`fixedEntryMatch` 已處理）。
